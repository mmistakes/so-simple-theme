## 시작한 이유

같은 결함(너트 풀림, nut_loose)을 놓고 탐지(YOLOv5) 방식과 분류(EfficientNet-B0) 방식으로 각각 풀면 실제로 뭐가 다른지 직접 비교해보고 싶었다. 데이터 비율(100/80/60/40%)과 증강 여부까지 바꿔가며 총 24가지 조합(YOLOv5 16개 + EfficientNet-B0 8개)을 전부 학습시켜서,  숫자로 차이를 확인하는 게 목표였다.

## 무엇을 어떻게 학습시켰나

- **탐지(YOLOv5s)**: 정상+불량 2클래스로 같이 탐지(exp1) / 불량만 1클래스로 탐지(exp3), 각각 증강 유무(exp2, exp4)와 데이터 비율(100/80/60/40%)을 조합해 16개 실험. 640px 입력, batch 16, epoch 500. `ultralytics/yolov5`의 `train.py`/`val.py`를 그대로 호출하는 구조로, 별도 커스텀 학습 루프는 만들지 않았다.
- **분류(EfficientNet-B0)**: 탐지된(또는 정답) bbox를 여백 포함해 crop한 이미지 한 장을 nut/nut_loose로 분류. ImageNet 사전학습 가중치를 불러와 전체 파인튜닝(fine-tuning). 증강 유무(exp5/exp6) × 데이터 비율 4단계로 8개 실험. 224px 입력, epoch 100.
- **공정 비교를 위한 장치**: 24개 실험 전부가 학습에 한 번도 쓰지 않는 고정 test 50장(분류는 여기서 crop한 401장)을 최초에 딱 한 번만 뽑아서 공유했고, 100/80/60/40% 데이터가 서로 중첩(40%⊂60%⊂80%⊂100%)되도록 구성해서 "데이터를 줄이면 얼마나 나빠지는가"만 순수하게 비교할 수 있게 했다.
- **파이프라인 순서**: 데이터 분할 → (탐지용) 오프라인 증강 생성·배분 → YOLOv5 학습·검증 → 결과 집계 → (분류용) crop 데이터셋 생성 → EfficientNet 학습 → 결과 집계, 총 8개 스크립트로 나눠서 순서대로 실행하는 구조로 짰다.

## 배운 것 1 — 지표가 높다고 "더 좋은 모델"은 아니다

같은 결함인데도 EfficientNet-B0(분류)의 불량 Recall(0.91~0.94)이 YOLOv5(탐지)의 불량 Recall(최고 0.761)보다 훨씬 높게 나왔다. 처음엔 "분류 모델이 더 좋다"고 생각했지만, 사실은 두 모델이 푸는 문제 자체가 달랐다 — 분류는 위치가 이미 주어진 crop 한 장을 판별만 하면 되고, 탐지는 이미지 전체에서 위치까지 찾아야 한다. 지표를 비교하기 전에 그 지표가 정확히 어떤 난이도의 문제에 대한 답인지부터 확인해야 한다는 걸 체감했다.

## 배운 것 2 — "증강"은 생각보다 다루기 까다로운 개념이다

YOLOv5의 exp1/exp3를 "비증강"이라고 이름 붙였는데, 실제로는 YOLOv5 자체가 기본값으로 mosaic·HSV 지터·좌우반전 증강을 계속 돌리고 있었다. `--hyp` 옵션을 따로 넘기지 않으면 라이브러리 기본 하이퍼파라미터가 조용히 적용된다는 걸 몰랐던 것 — "내가 안 켰으니 꺼져있겠지"라고 프레임워크의 기본 동작을 확인 안 하고 넘어간 게 문제였다. 증강을 만드는 방식도 문제 유형에 따라 다르다는 걸 알게 됐다 — bbox가 있는 탐지는 증강할 때마다 좌표를 다시 계산해야 해서 디스크에 미리 만들어두는 게(오프라인) 편했고, 좌표가 없는 분류는 학습 중 매 epoch 즉석에서 변형하는 방식(온라인)이 오히려 더 다양한 조합을 보여줄 수 있었다.

## 배운 것 3 — 모델링보다 환경 디버깅에 시간이 더 든다

Windows에서 GPU 학습 환경을 갖추는 데 예상보다 훨씬 손이 많이 갔다. CPU 전용 PyTorch가 깔려 있어 GPU가 있어도 안 쓰였던 것(`torch.cuda.is_available()`로 확인), DataLoader worker를 너무 많이 쓰면 크래시가 나고 0으로 낮추면 GPU가 노는 것, subprocess로 다른 스크립트를 실행할 때 필요한 로그가 stdout이 아니라 stderr로 찍혀서 로그 파일이 계속 빈 채로 저장되던 것 — 전부 모델 구조나 하이퍼파라미터와는 무관한, 순전히 실행 환경 문제였다. 실제로 학습 코드를 짜는 시간보다 "왜 이게 이렇게 느리지/안 되지"를 진단하는 시간이 더 길었다.

## 배운 것 4 — 결과를 다 만든 뒤에도 한 번 더 의심해야 한다

보고서를 완성한 뒤 스스로 다시 검토해보니, 표에서 "최고값"이라고 강조한 셀이 실제로는 1등이 아니라 2등 값에 붙어 있었다. 혼동행렬 정규화 방향을 설명한 문구가 실제 이미지와 반대로 적혀 있었고, 표본 수를 잘못 적어놓은 곳도 있었다. 전부 눈으로 봤을 땐 그럴듯해서 처음엔 지나쳤던 부분들이다. 결과를 다 만든 뒤에도 "이 숫자가 실제로 맞나"를 원본 데이터와 대조해보는 단계가 왜 필요한지, 이번에 직접 틀렸다가 잡아보고서야 확실히 느꼈다.
